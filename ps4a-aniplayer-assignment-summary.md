# PS4a: Static Animation Player

This file summarizes the assignment described in `ps4a-aniplayer.pdf` and the starter code in `AniPlayer-starter/`.

## Project goal

Build an `AniPlayer` program that loads an animation from a JSON file and renders the first frame of the animation in an SFML window. In Part B, the player will be extended to tween between keyframes and animate movement over time.

The assignment is explicitly about:

- reading animation data from JSON
- representing shapes and keyframe data in C++
- using a factory to construct the right component type
- using the composite pattern to organize scene graph objects
- rendering the scene to a window using SFML

## Assignment context

The PDF describes the project as an animation assignment based on inbetweening (tweening):

> certain key frames are created, and intermediate frames are generated by interpolating between those key frames.

The task is not to hand-code every frame. Instead, the program should load a JSON specification and render a scene that can be animated smoothly.

The background color for the window is specified as:

- `0x01010101`

## Core program behavior

The final `AniPlayer` must:

- take a JSON filename as a command-line argument
- load the animation data from that file
- build a scene graph made of components
- display the first frame correctly in a window
- later support tweening and movement (Part B)

The assignment states: "For Part A of this assignment, you will load the video and draw the first frame. In Part B, you will add tweening and movement."

## JSON format

The animation data is stored in JSON, using `nlohmann/json` for C++.

Example structure:

```json
{
  "shape": "circle",
  "radius": 50,
  "keyframes": [
    {"t": 0, "x": 50, "y": 50},
    {"t": 5, "x": 300, "y": 300}
  ]
}
```

JSON supports:

- objects
- arrays
- strings
- numbers
- booleans
- nested objects

The assignment emphasizes that JSON field order does not matter, and that the `json` library can parse a file or a string directly.

## Required C++ classes and namespaces

The project is expected to use a namespace named `AP` and include these types:

### `AniPlayer`

Fields include:

- `width` (`unsigned int`, required)
- `height` (`unsigned int`, required)
- `scene` (`Component`, required)
- `bgm` (`string`, optional)

This class is responsible for the overall animation player and its window sizing.

### `KeyFrame`

Fields include:

- `t` (`float`, required)
- `x` (`float`, default `0`)
- `y` (`float`, default `0`)
- `scale-x` (`float`, default `1`)
- `scale-y` (`float`, default `1`)
- `theta` (`float`, default `0`, in degrees)

This class is central to interpolation and tweening.

### `Component`

Base class for all drawable objects.

Fields include:

- `shape` (`string`, required)
- `color` (`string`, hex, default `FFFFFFFF`)
- `keyframes` (`KeyFrame[]`, default empty list)

The assignment specifically requires a factory function:

- `Component::fromJson(const Json& data)`

This factory returns a `std::unique_ptr<Component>` and chooses the correct concrete component type from the JSON.

## Concrete component types

The assignment says you will create several component subclasses:

### CircleComponent

- `radius` (`float`, default `0`)
- `sides` (`size_t`, default `30`)
- drawn centered at the given position

### RectangleComponent

- `x`, `y`, `width`, `height`
- defaults are zero

### ImageComponent

- `file` (`string`, required)
- relative path to an image resource

### TextComponent

- `text` (`string`, default empty)
- `font` (`string`, required)
- drawn with its upper-left corner at the specified position

### CompositeComponent

- `children` (`Component[]`, empty by default)
- children are positioned relative to the parent composite object

## Design pattern requirements

The assignment expects two major design patterns:

### 1. Factory pattern

The project should avoid repeated conditional logic for creating different component subclasses.

Instead, `Component::fromJson(...)` should inspect the JSON and construct the correct kind of component automatically.

This is important because:

- client code should not need to know each concrete type
- the factory centralizes component creation
- it avoids duplicated branching logic
- unknown component types should throw an exception

The assignment explicitly notes that factory methods normally return pointers and that smart pointers (`unique_ptr`) are preferred here.

### 2. Composite pattern

A composite component is used to organize multiple scene elements as a hierarchy.

The PDF states that the animation is composed of many figures, some related, and that the composite should render its child components relative to itself.

This is the pattern that supports nested scene structures and grouped transforms.

## Drawing and transformation rules

The document specifies several rendering rules:

- `CircleComponent` and `ImageComponent` are centered at their given positions
- `TextComponent` uses its upper-left corner as its anchor
- `CompositeComponent` draws children relative to the parent composite
- the scene is rendered in the window with the correct size based on the JSON `width` and `height`

The assignment also uses `sf::Drawable`, `sf::Transform`, and `sf::RenderTarget` in the starter code.

## Part A / Part B split

### Part A

The static version requires:

- loading JSON
- building the scene tree
- drawing the first frame correctly
- setting the window size
- parsing component shapes and data
- handling default values and invalid input

### Part B

The second part adds interpolation and motion:

- tweening between keyframes
- applying transforms (position, scaling, rotation)
- moving figures over time
- animating based on the `t` field within keyframes

The starter headers show this clearly with methods such as:

- `Component::tween(sf::Time time)`
- `KeyFrame::tween(KeyFrame alt, sf::Time t) const`
- `KeyFrame::transform(sf::Transform& state) const`
- `AniPlayer::tween(sf::Time time)`

## Practical implementation notes

A student completing this assignment should expect to:

1. parse `width`, `height`, and `scene` from the main JSON
2. create a `Component` factory using JSON data
3. support several component subtypes with distinct transforms and drawing logic
4. use `std::unique_ptr` to manage object ownership
5. calculate the current frame between keyframes by interpolation
6. draw children relative to a composite parent
7. respect default values and type conversion rules
